# Control Center Module

Canvas-based network topology editor built on [ReactFlow](https://reactflow.dev/) (xyflow v12). Peers, groups, policies, and networks are nodes; policies connect them. Live mode shows the real account; Draft mode is a local editor whose changes deploy as a batch.

> Keep this file in sync when the architecture or the rules below change — but keep it SHORT. Details live in the code.
> The full node-interaction matrix (connects, drops, menus, rename/delete rules) is exercised by the control-center e2e suites (`e2e/tests/control-center-draft-*.spec.ts`) — keep those in sync when interaction behavior changes.

## Architecture

Provider tree (page.tsx), outermost first:

```
DraftModeProvider → DragAndDropProvider → ReactFlowProvider → PoliciesProvider
→ AIProvidersProvider → PeersProvider → CanvasStateProvider → GroupsProvider → DraftChangesetProvider
→ DraftHistoryProvider → ControlCenterPolicyProvider → ControlCenterUIProvider
→ ControlCenterCanvas
```

- `useCanvasState()` — nodes, edges, setters, currentView, selection state. Changes identity on EVERY nodes update: node/edge components must never use it. They use the narrow contexts instead: `useCanvasUI()`, `useDestinationGroup()`, `useNetworkHover()`, or ReactFlow `useStore` selectors with value equality.
- `useControlCenterUI()` — navigation, onNodeClick, network options.
- `useControlCenterPolicy()` — policy modal setters + `drawPolicyOnCanvas` / `updateDraftPolicy` / `openAgentPolicy`.
- `useDraftMode()` — isDraft, active tool, draft modals/drill-down state.
- `useDraftChangeset()` — tracked draft changes (React state only; not persisted).
- `useGroups()` — group CRUD + dropdown options.

Data flow: `useControlCenterData()` fetches everything (SWR) → view hooks (`usePeerView`, `useGroupView`, `useUserView`, `useNetworkView`) build node/edge graphs → `useSelectNodeHandlers({ views })` owns navigation, the view-init effect, and the shared `fitView` → `ControlCenterUIProvider` wires it together. Circular deps (node onClick → handlers → view builders) resolve via refs on CanvasStateProvider (`forceSingleGroupViewRef`, `refreshLiveViewRef`).

Key directories under `control-center/`: `contexts/` (ControlCenterContext, DragAndDropProvider, policy modals), `header/` (top chrome + FlowSelector), `menus/` (canvas/node context menus), `panels/` (destination-group, peer-groups, routing-peers), `nodes/`, `edges/` (+ ConnectionLine), `handles/`, `toolbar/`, `hooks/` (data, `views/`, draft logic, layout reconcilers), `utils/` (graph-builder, layouts, canvas-transition, pure testable logic), `draft/` (draft-mode UI + changeset/history contexts; `modals/` holds the Draft\* modals, `changeset/` the review views).

## Views (live)

Peer / Group / User: select node on the left → policies (x500, 60 pitch) → destinations (groups + resources as ONE column, x1000, 100 pitch). Built with `applyD3HierarchicalLayout(nodes, edges, 400, 120, view, DEFAULT_LAYOUT_CONFIG)`. Policies sorted by enabled; the GROUP view additionally name-sorts each policy's destinations/sources. GROUP view also shows policies where the selected group is only a DESTINATION, mirrored to the left (sources at x-1000 → policy at x-500 → selected group); those policy nodes carry `data.side === "left"`, which the layout uses to split the policy column.

Agent Network overlay (`views/agent-network-overlay.ts`): when the feature is enabled, the PEER and GROUP views also append `source → agent-policy-<id> → provider-<id>` for every agent-network policy authorizing the group (the peer view unions this over the peer's groups). Agent policy nodes share the policy column, providers the destination column. Data comes from `useAIProviders()` (which owns the flag-gated fetches) and clicking an agent policy opens `AgentPolicyModal` via `openAgentPolicy`.

Networks: all networks as interactive frames (resources as child rows, capped at 6 with a "+N more" cell) — sources column (160 pitch) → policy nodes (x500 + `POLICY_COLUMN_Y_OFFSET`, 90 pitch — same anchor as the other views so policies don't jump on view switch) → staggered frame grid (`packFrameGrid`, centered on the columns' midline). Clicking a frame drills into the single-network view (`drilled-layout.ts`, shared with draft). Focus mode is EXPLICIT (a node's context-menu Focus item or the header's armed Focus tool — live AND draft; left-clicking a group only opens its panel, no dim) and dims everything off the node's edge path via `cc-dimmed` and rings the focused node; policy editing lives in the node's right-click menu (live: Edit, Disable/Enable and Delete, permission-gated; Edit's "you are in live mode" confirmation is deferred to Save, via `usePolicies` + `refreshLiveViewRef`).

## Draft mode

- Entering draft rebuilds the canvas from the policies visible in the live view (`useDraft`): source groups/peers → policy → destinations. Live network frames carry over as existing-network frames; destination groups whose resources live in exactly one carried network fold into that frame as `resourceGroupNode` rows.
- **Layout parity**: the draft build mirrors the live view it was entered from (same column x/pitch, same sort — see Views). The build layout lives in `utils/draft-build-layout.ts` (`applyDraftBuildLayout`), shared with the toolbar's Auto Arrange so arranging an untouched draft reproduces the entry layout exactly (drill-downs re-run `applyDrilledLayout`). Destinations restack as one column (x 1000) with sides resolved by edge direction, ordered by first policy edge — including in a frames draft, where the frame grid then starts past that column instead of at its bare `FRAME_GRID_BASE_X` (the hierarchical layout buckets by node TYPE, so a destination peer would otherwise sit on the sources at x 0 and a standalone resource inside the frame grid); existing destination resources get `draftNetwork` stamped so they don't show "No Network". Draft nodes adopt their live twin's measured size (`initialWidth/Height`, incl. renamed ids like self-ref `dest-group-…` clones) — React Flow hides unmeasured nodes for a frame, which read as flicker on the mode switch.
- Changes are tracked as CRUD-shaped entries in `DraftChangesetContext` (groups/policies/resources: create+update+delete; networks: create+update+delete; routers: create+update), coalesced per entity. Editing an EXISTING network/router in draft records an `update-network`/`update-router` change instead of a live PUT (`DraftNetworkEditModal` / `DraftRoutingPeerModal` run the live modals in `useSave={false}` mode and hand the values to the changeset). Draft state (the changeset and the canvas) lives only in React context for the lifetime of the draft session — nothing is persisted, so a reload rebuilds from live rather than restoring. A policy enters the changeset once it's *trackable* (`isTrackablePolicy` — both sides set, referenced draft resources tracked); a one-sided policy stays canvas-only. A trackable policy that references an uninstalled placeholder peer is still listed (as an ordinary change) — that peer's own `install-peer` issue is what blocks the deploy, and installing it re-records the policy with the real id (`usePlaceholderUpgrade`). `isDeployablePolicy` is the stricter gate, asserted by `useDeployChangeset` at the POST/PUT itself: the UI's blocking-issue check is keyed on a different entity, so the sink does not trust it. A policy left with nothing on EITHER side is not an update at all — `trackUpdatePolicy` records a `delete-policy`, since the API rejects a rule that authorizes nothing. That is for an EXISTING policy and for an emptying the user did themselves; a DRAFT policy emptied by a group deletion keeps its `create-policy` change (tagged, and carrying an `Incomplete` blocking issue) rather than being dropped, because nothing can restore a change that is no longer in the changeset. One bare side is enough (`isEmptiedPolicy`), and it has to be: the deploy sink asserts on `isDeployablePolicy`, which wants both sides present, so a one-sided policy recorded as an update is a change the deploy is guaranteed to refuse — mid-run, after earlier changes have already landed, and with no warning at confirm time. `isEmptiedPolicy` stays narrower than `isDeployablePolicy` on purpose: a policy pointing at an uninstalled placeholder peer is a real pending change blocked by that peer's own `install-peer` issue, not a deletion. `update-policy` and `delete-policy` for one policy are MUTUALLY EXCLUSIVE and every tracker enforces it both ways: `update-policy` deploys before `delete-policy`, so a policy carrying both would be written and then destroyed. Rebuilding an emptied policy therefore clears the delete, deleting it clears the update, and a toggle is ignored while a delete stands. `useDeployChangeset` refuses the whole deploy if a changeset ever carries both. Deleting an EXISTING group also has to leave every policy naming it (the API refuses the group DELETE otherwise), so `deleteGroups` records those policy writes tagged with `groupDeletion` — the ids stripped plus the pre-strip policy. The strip is measured over `policySnapshots()`, which is the canvas UNIONED with live `/policies`, not the canvas alone: a blank draft draws no policies and a group dragged in from the components panel arrives without them, so a live policy naming the group kept it and the deploy — which sends `delete-group` LAST — landed everything else and then had the API refuse the DELETE, identically on every retry. The canvas copy wins where a policy is drawn (it carries pending draft edits); a policy already marked for deletion is skipped, since its own DELETE deploys first and a strip would record an `update-policy` that supersedes it. DRAFT policies are stripped too — a `create-policy` deploys BEFORE the `delete-group` — and carry the tag on the create change, which `restoreDeletedGroupInPolicies` restores in place rather than dropping, since a create change is the user's own work. Discarding the `delete-group` then rebuilds each write from that baseline minus the deletions that REMAIN (`restoreDeletedGroupInPolicies`), dropping it entirely when there are none; without that the deploy strips the group anyway and revokes access the user just cancelled. Deletions ACCUMULATE across separate actions: a second deletion's write supersedes the first's, so `mergeGroupDeletions` unions the stripped ids and keeps the EARLIEST baseline — the later one was computed from a canvas policy the first deletion had already stripped, so only the first still holds every group being taken out. An ordinary edit does NOT clear the tag: it was computed from the same stripped canvas, so the strip lives on inside it, and clearing the tag stranded it there — discarding the `delete-group` then deployed the revocation the user had just cancelled. `mergeGroupDeletions` REBASES the tag onto the edit instead (the stripped groups go back in to form the new baseline) and marks it `handEdited`, which is what keeps such a write alive when the last deletion is discarded rather than dropping the user's edit with it. BOTH orders have to set it: in the edit-then-deletion order the deletion's write supersedes the edit, so the tag arrives as `incoming` with no earlier tag to inherit the flag from — but the edit is inside that incoming baseline all the same, since the baseline was read off a canvas the edit had already been applied to. `supersedesUserWrite` (an untagged `update-policy`, or the `create-policy` of a draft policy) is what tells that apart from a write that exists only for a deletion. The one edit that does clear the tag is one that leaves the policy authorizing nothing: that is a request to delete the policy, and a cancelled group deletion must not resurrect it — which is also why `trackDeletePolicy` does NOT carry the tag onto the `delete-policy` it records. Discarding the policy write itself is the mirror case and is handled at the discard, not on the change: restoring the policy from LIVE revives every group it names, so `pendingGroupDeletionWrite` re-records the strip under the SAME change id for any group a `delete-group` is still pending for. It reads live rather than the discarded change's tag, because an untagged write (a toggle) strands the deletion just as thoroughly. Without it the deploy lands every other change and then fails on the group DELETE, which the API refuses while any policy references the group.
- Deploy (`useDeployChangeset`) runs in dependency order: group creates/updates → networks → resources → routers → policies → deletes (policy, resource, group); client ids (`new-…`) resolve to real ids as creates succeed. Group and network NAMES are not unique account-wide, so a by-name ref that matches more than one live entity fails the deploy instead of picking one, and an unresolvable ref fails rather than travelling to the API as a name in an id field (a create earlier in the same run settles its own name). A ref is a draft group's NAME or a live group's raw id, and the ID is resolved FIRST — it is the unambiguous half of that union, and a group *named* after another group's id would otherwise capture every ref to that id. `previewResolvers` resolves in the same order and the two must never disagree about which group a ref denotes: the code view is what the user approves. A change is skipped on retry only when its PAYLOAD is unchanged: coalescing keeps a change's id across edits, so an already-created entity whose change was edited deploys as a PUT against the id its POST returned, never a second POST. Resources and routers are addressed UNDER a network, so `createdIds` stores the network the create actually ran against alongside the id: if the draft has since pointed the change at a different network, the retry refuses instead of PUTting to a path the object does not live at. That retry PUT REPLACES the member list, so `create-group` merges onto a fresh read exactly as `update-group` does; its removals are derived by diffing against what the earlier run sent (the signature IS the serialized change), so a member added from outside the draft survives while one the user dropped from the draft is really removed.
- Placeholder peers ("User Device"/"Server"/"Agent") are canvas-only until installed/selected; `usePlaceholderUpgrade` swaps them in place and re-records referencing changes with the real peer id. The `install-peer` entry is NOT removed on upgrade — it's marked installed (`installedPeerId`) and stays a non-blocking row so an open Review & Deploy / install modal never empties under the user; deploy skips it and `clearChanges` drops it after.
- Routers have NO canvas node: a routing peer exists only as a `create-router`/`update-router` entry, and a frame's routing-peer count is read from the changeset. There are no routing edges, so removing a peer or a frame cannot cascade to a router change.
- Server/agent placeholders are matched to their installed machine by a **throwaway group** named `<name> (Draft)`. It is an ORDINARY group — the API has no hidden flag, so it does show up in group lists — it is just kept off the canvas and out of policies, and it is not a changeset entry. `DraftInstallPeerModal.resolveAutoGroups` creates it via `POST /groups` when the setup key is generated and puts its id on the key as an `auto_group`; the registering peer lands in it, so `useDraftPeerUpgrade.findByGroup` matches unambiguously (hostname is a fallback, and the only mechanism for user devices, whose key carries no auto_group).
- `usePlaceholderArtifacts` owns the key and the group from the moment they exist: `registerArtifacts` on creation, `deleteArtifacts` once the peer registers, `flushArtifacts` on draft exit. A non-empty registry is therefore a second reason `DraftLeaveGuard` must arm (`mustSweep`, not just `changeCount > 0`) — removing the last placeholder takes the changeset to zero while its key and group are still real, and every exit that sweeps them runs through `discardAndExit`. Removing a placeholder does NOT delete them — undo can bring the node back, and the registry (not a canvas walk) is what guarantees a removed placeholder's artifacts still get torn down. It DOES revoke the setup key (`revokeSetupKey`): the key is the one live credential here, deferring outright left it usable for the rest of the session, and revoking is reversible in the way deleting is not. Teardown deletes the **setup key first** — that dissolves the `auto_groups` link the group delete would be refused for, and the key is the one artifact that is a live credential, so it must not be what a failure elsewhere leaves behind: delete the key → (only if that failed) unlink the group from `auto_groups` → empty the group's peers → delete the group → revalidate `/peers` + `/groups`. No step aborts the rest; each records its own failure, and one failure strands at most one object. A failed step raises a toast naming the leftover; it is a real object only the user can remove.
- Pure draft logic is factored for unit tests (`npm run test:unit`): `utils/draft-connect.ts`, `utils/node-capabilities.ts`, `utils/frame-view.ts`, `utils/helpers.ts`, changeset tests.

## Rules & gotchas (hard-won — don't regress these)

**Performance** (the canvas re-renders ~2700 fibers if you get this wrong):

- Every callback/object prop on `<ReactFlow>` must be identity-stable (`useStableHandler`, module-level constants).
- Edges subscribe to endpoint nodes via `useEdgeNodeRect`, never `useInternalNode`. Nodes use `useConnection` in SELECTOR form only.
- Edge dash animation is the shared `cc-animated-edge` CSS class (paused during interaction via `.cc-interacting`), never SMIL.
- No data-fetching hooks in node components that render per-frame; frames fetch router rows lazily on popover open.
- Drag handlers must return the same array from `setNodes` when nothing changed; layout reconcilers, draft persistence, and history capture all skip while dragging and pre-check structurally before any full-canvas JSON.stringify.
- Always-mounted draft consumers that only need node data subscribe via `useStructuralNodes()`.

**Camera / transitions**:

- The shared `fitView` (useSelectNodeHandlers) waits for node measurement; the FIRST fit after mount hides the viewport (`cc-prefit` class + instant fit) so warm-cache remounts don't flash nodes at the origin.
- Drill-downs use `drillInto` / `drillOutOf` (canvas-transition.ts); view-init fitView is suppressed while a transition runs. Browser Back exits drill-downs via `useDrillDownBrowserHistory`.

**Behavior**:

- Saving a policy in live patches the canvas from the PUT response (`refreshLiveView`) — no fitView, no refetch wait.
- Frame-ness is `data.frame` (or `network-new-` id = draft network), not an id prefix; `getNetworkRef` resolves a frame to real or client id.
- Policy edges to framed resources attach to the frame in the parent view and to the resource when drilled (`useFrameEdgeAttachment`).
- Leaving draft is guarded on `mustSweep` by `beforeunload` for reloads, a popstate sentinel for browser Back, and — for in-app navigation — `useGuardedRouter`. That router, NOT `useRouter`, is what consults the guard: the App Router exposes no global router instance to patch, so there is nothing to install a guard on centrally and every navigating call site has to opt in. The capture-phase click interceptor in `DraftLeaveGuard` covers only `<a href>` clicks, so it does NOT see the dashboard chrome, which navigates from `<button>` handlers: `SidebarItem`, `Header`, `UserDropdown`, `NavigationUsageInfo`, `TrialNavigationInfoCard` and `LimitsReachedModal` therefore use `useGuardedRouter` (it passes straight through when no guard is installed, so it is a drop-in). Anything else added to the persistent chrome must do the same — a raw `useRouter().push` there walks off the draft silently, stranding a live setup key. Watch for chrome that swaps itself out: `NavigationUsageInfo` early-returns `TrialNavigationInfoCard` on a trial account, so converting the outer component alone left trial accounts unguarded. `SidebarItem.test.tsx` and `TrialNavigationInfoCard.test.tsx` pin this.
- `getCanvasWarnings` is UNCALLED on purpose and its cases are unreachable — do not wire it up. A draft resource node is only born on the editor's save (`addBlankNode`: "a resource needs an address, so its card is only created on modal save"), so it is tracked from birth: one with no network is a `create-resource` change carrying the `No Network` blocking issue, and its node also shows an actionable amber "No Network" button. A policy pointing at an uninstalled placeholder is blocked by that peer's own `install-peer` issue. Every state it warns about is already on a changeset row or on the node itself.
- Deletes always confirm ("marked for deletion…"); Removes never confirm. A Remove is not canvas-only: stripping a group/peer/resource out of a policy records the resulting `update-policy` change (`deferPolicyStrips` → `updateDraftPolicy`), reviewable and discardable like any other. An EXISTING policy or framed resource still has no Remove — taking either off the canvas wholesale is a deletion, which must confirm — and `canRemoveNode` excludes them so keyboard Delete can't either. Removing (or deleting) a group that holds absorbed placeholders nets their pending membership adds back out (`trackRemoveGroupMembers` with `pendingOnly`), so no empty "Modify" row survives the sweep.
- Draft keyboard shortcuts go through `useControlCenterShortcuts` (draft-only, input-aware).
